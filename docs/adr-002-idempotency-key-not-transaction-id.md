# ADR-002 — Why the idempotency key is not the transaction id

**Status:** accepted, 2026-09-10

## Context

A client that sends a transfer and never receives a response does not know
whether the money moved. Its only safe move is to send the request again, which
means the server must be able to recognise the second request as the same
attempt and not move the money twice.

Something has to identify "the same request". The tempting candidate is already
in hand: the transfer's own id, generated by the client. One identifier instead of
two, no extra column, no extra index.

## Decision

Two separate identifiers, and a third value to adjudicate between them.

`transfers.id` is the transfer — a business entity, server-generated.
`transfers.idempotency_key` is the attempt — client-supplied, carried in a
required `Idempotency-Key` header, and `UNIQUE`.
`transfers.request_fingerprint` is a SHA-256 of the canonical payload: source,
destination, amount, currency.

The key alone decides nothing. When a key is already taken, the fingerprint
decides what happened:

- **Same key, same fingerprint** — a retry. Return `200` with the original
  transfer, read back from the stored row.
- **Same key, different fingerprint** — a key reused for a different request.
  Return `409` and write nothing.

Detection is left to the unique index rather than a preceding `SELECT`, for the
same reason as ADR-001: two simultaneous retries would both find the key free.
PostgreSQL blocks the conflicting insert until the transaction holding the key
commits or aborts, so when the violation surfaces the winning row is already
committed and readable. The race is removed rather than narrowed.

## Alternatives considered

**Use the transfer id as the idempotency key.** Rejected because it fails in both
directions, and a client can only avoid one failure at a time.

A client that treats the id as belonging to the *request* will generate a fresh
one when it retries — which is the natural thing to do, since the previous
attempt appeared not to exist. Deduplication is lost silently and the money moves
twice.

A client that treats the id as belonging to the *entity* will reuse it, correctly,
across retries — and will also reuse it if it later constructs a different
request from the same business object. The server, having only the id to go on,
returns the first transfer's result. The client reads a success and believes its
new request was applied. Nothing anywhere reports an error.

The two behaviours are both reasonable readings of one identifier, and no server
holding only that identifier can tell them apart.

**Return the first result for any key reuse.** The convenient answer, and the one
that hides the failure above. Rejected for the same reason: it turns a client bug
into a silent wrong outcome. A `409` is noisy and can be acted on.

**`422` rather than `409`.** `409 Conflict` is the accurate status — the request
conflicts with existing state, and the state is the obstacle rather than the
request's own contents. `422` is used in this API for requests the ledger
understood and refused on its merits, which is a different situation.

## Consequences

**The response body of a replay must be read, not rebuilt.** A body reconstructed
from the retry's own payload would carry the same accounts, amount and currency,
and would be wrong: a different transfer id and timestamp, describing a transfer
that never happened. Both paths therefore build the body from one place. The test
that asserts the two bodies are identical was checked against this exact mistake
and does catch it.

**The fingerprint must be canonical, or safe retries break.** It is computed over
a fixed field order in code, not the order the JSON keys arrived in. Without that,
a client whose serialiser orders fields differently on retry would receive a
`409` — a failure it cannot diagnose and cannot resolve by retrying, which is
strictly worse than the problem being solved.

**The fingerprint covers the payload and nothing else.** Not the caller, because
there is no authentication in this service. If one were added, identity would
have to enter the fingerprint, or two clients could collide on a shared key and
one would read the other's transfer.

**Keys are kept forever.** There is no expiry and no cleanup, so `transfers`
grows without bound and a key can never be reused even years later. A production
system would expire keys after some window and accept that a retry arriving after
it is treated as new. That is deliberately out of scope here, and it is the most
significant thing this design leaves undone.

**Clients carry a real obligation.** They must generate a fresh key for each new
request and reuse it only when retrying. The `409` is what makes that obligation
visible instead of silently absorbed — which is the entire point, and also the
reason this is a contract worth documenting rather than an implementation detail.
